# Checkout 历史索引切换（本地已准备，生产未执行）

用户于 2026-10-24 批准本轮兼容迁移。新代码保留旧无 Customer 的未结付款保护，
并停止在购买、积分发放或删号请求中遍历全商户 Checkout 历史。

## 发布前置与顺序

1. 在隔离数据库重放迁移、验证归属索引与旧付款回归。确认部署和生产迁移另获授权。
2. 安排结账切换窗口，暂停旧版 Checkout 写入与相关调度；保留 Stripe Webhook 的
   可重试投递，不对尚未落库的付款返回虚假的成功。应用本次数据库迁移和代码。
3. **等待所有旧版请求/后台任务退出后**再启动导入。不得让旧版 customer_email
   Checkout 写入跨越冻结边界。新代码在迁移边界未建立前拒绝新 Checkout；旧账号
   的付款/积分/删号在索引完成前保持可重试安全阻断，不视为付款未发生。
4. 在受控服务器环境使用当前项目、正确 Stripe 商户/Live 环境和数据库运行：

   ```sh
   node --experimental-strip-types scripts/import-checkout-history.ts
   ```

   脚本只读 Stripe，每次最多处理 10 页。首次调用持久化固定时间边界；每页在同一
   数据库事务内写入归属索引和游标。重复运行直至输出 `complete: true`。
   失败不得手工标记完成或移动游标；修复错误后使用相同进度继续。脚本不加载 `.env`，
   应由批准的运行环境注入变量，不在命令或日志中显示凭据。
5. 回读 `CheckoutHistoryMigration` 的固定边界、完成时间，以及 `LegacyCheckout`
   归属/旧预约 ID；核对无 Customer 未付款、已付款未结算、旧升级和已删除重建账号。
6. 恢复结账与调度，确认重投 Webhook、续费、年付积分、升级确认、删除账号与已保存
   卡片行为。按独立授权执行正式冒烟与真实支付验收。

## 保持的边界

- 不把截断历史当作没有付款。Customer/索引查询有异常时继续安全阻断。
- 新 Checkout 在写入前绑定带账号创建版本的 Customer，参数与预约保持幂等。
  丢失回复仅在本 Customer 范围恢复；旧无 Customer 预约从完成的归属索引恢复。
- 已有会话以 Stripe 当前状态为准，不用迁移时的付款状态发积分或授权删除。
- 同账号每小时最多创建 12 个新 Checkout 预约；复用已有预约不增加次数。
- 新表启用 RLS，拒绝 `PUBLIC`、`anon`、`authenticated`、`service_role`，仅给
  `flownana_app` 服务器 CRUD 权限和 Policy。应用与迁移账号继续分离。
- 这一步尚未在生产执行。数据库迁移和旧会话导入缺一不可，不能只发布代码。
