## 1. 一次 Allow 完成两项同意

### 用户流程

- 新访客看到既有底部轻量提示，同一组 Allow / Reject；说明基础统计、广告 Cookie、
  登录后购买时的邮箱哈希匹配、可撤回。广告个性化始终关闭。
- 点 Allow 后立即允许当前浏览器基础统计与广告衡量。匿名阶段尚无邮箱，
  不发送邮箱或猜测身份；记录有版本和时间的广告用途许可。
- 首次成功 Google 登录、服务端确认邮箱已验证后，自动把这次匿名许可绑定到该账户。
  页面不用再点 Allow，后续新付款可以使用该账户已验证邮箱哈希。
- 绑定失败先保持基础统计和错误/重试状态；显示准确的广告状态，不把浏览器选择
  或“正在绑定”当作服务端账户授权已完成。失败不阻断登录、生成或付款。
- 未登录 Allow 为一次新的匿名许可，仅能绑定一个账户；绑定成功后不能给其他账户复用。
  换号无有效账户许可则提示选择；返回原账户可恢复仍有效的本人许可。
- 登出停止本浏览器后续账户邮箱共享，已绑定账户许可仍可在 Privacy 显示和撤回；
  不把登出当作允许其他账户，不把新建匿名 intent 用来自动绕过换号确认。
- Reject 同时停止两项、撤回匿名待绑定许可和本浏览器当前/待确认账户许可，
  迟到登录/允许/绑定请求不得恢复它。断网撤回沿用持久待确认与重试机制。
- GPC、已拒绝、旧基础统计同意、地域默认统计均不能视为新的广告许可。
  旧仅基础同意用户得到一次新用途提示；已拒绝者通过主动 Privacy 再选择。
- US/JP/TW 基础统计地域默认规则继续适用，但新广告用途在这些地区也显示一次提示。
  关闭 × 只收起提醒，未选择不授权广告；首次/主动打开均共用相同说明与按钮。

### 服务端实现建议

- 新增最小匿名许可记录（BrowserMeasurementConsent），随机不可猜测 ID，
  保存政策版本、两项用途、服务端 grantedAt、expiresAt、撤回状态及一次账户绑定状态。
  建议有效期 180 天；过期重新询问，政策实质改变用新版本重新确认。
- 浏览器仅存签名的 HttpOnly、Secure、SameSite=Lax 回执/引用，不存邮箱。
  浏览器广告状态须在 API 成功后更新；广告储存和用户数据分别明确记载。
- POST 同源、GPC 校验；绑定须真实登录、服务端验证邮箱、当前账户创建时间校验，
  匿名记录锁下单账户消费，并原子写入现有账户广告记录，支持请求幂等。
- account grant 保留匿名原始选择时间和后续实际绑定时间；购买增强仍要求真实账户
  绑定在付款发生前完成。付款后才绑定不补强旧购买，不能把选择时间用来绕过身份边界。
- 既有授权发送前再验证、邮箱变化、账户重建、撤回回执、开关停用规则继续覆盖。
- 不使用指纹、IP 或邮箱来猜匿名用户是谁，不合并不同账号历史许可。

### 验收

新访客 Allow -> 登录 -> 一次新付款无需二次允许；Reject -> 登录不绑定；
Allow -> 登录前撤回不绑定；绑定失败重试；并发登录/撤回；刷新、多标签、断网、
退出/同账号返回/换号、邮箱变化、重建账户、旧许可、US/JP/TW、GPC。
桌面/手机、所有 Privacy 入口、关闭重开状态一致。

## 2. 首次付费客户作为 Ads 唯一主要转化

**2026-10-12 后续决定：用户认为此实现过于麻烦，拒绝本节方案。以下为历史提案，
不作为开发授权。首次付费目标仍需讨论更轻的取舍；现有 purchase 主转化继续有效。**

### 口径

- 一位有效账户历史第一笔经 Stripe 核验、真实成功收取现金的付款，最多一条首购事实。
  零金额/免费/余额全额抵扣/手动标付不能占用首购；之后续费、升级、重新订阅不算首购。
- 首次现金付款即使以后退款，之后再次付款也不是新的首次付费客户；净收入和退款
  用财务口径处理。本轮不新增退款自动上报/价值调整。
- 用完整 Stripe 付款历史及可靠业务记录判定；不能以 new_subscription、账号新旧、
  现有 GA 是否记录过、授权是否存在来推断首次付费。
- 已付费但当时拒绝或缺少上下文，仍占用真实首购资格；之后允许不会让续费变首购。
- 无法证实历史完整性时标为待核对并告警，不能先当新客。不同账户是否同一自然人
  不通过邮箱猜测合并，指标明确为首次付费账户数。

### 实现建议

- 新增 FirstPaidCustomer 账本，当前 account ID + 创建 epoch 唯一，保存最早已验证
  invoice/payment ID、付款时间、验证状态；不依赖 GA 历史，不存广告邮箱哈希。
- 发布前对现有付费客户进行只读 Stripe 历史核对、分页完整遍历后填充内部账本；
  未完成的账户保守保留待核对状态。内部初始化不向 GA/Ads 回填过去购买。
- 同账户锁和唯一约束避免 Webhook/返回/重试/并发双计；考虑通知乱序，首次判定前
  核对最早成功付款，不能把最早到达 Webhook 的订单当最早付款。
- 保留 purchase = 全部符合原契约的真实订单；增加独立服务端 first_purchase =
  已核验首购。复用相同发生时间、交易 ID、统计上下文、授权依据与队列机制。
- first_purchase 为非标准电商事件；携带 transaction_id、实际首笔商品 value/currency
  便于 Ads 看首单价值。电商总收入继续只取 purchase，不累加两类事件的 value；
  first_purchase 去重靠内部账本和队列唯一键，不能假定 Google 会按其 transaction_id 去重。
- 这会从六个核心事件变为七个，属于明确的测量范围变更。GA 网页事件创建规则在
  浏览器侧执行，不能依赖它对当前 MP 服务端 purchase 生成首购事件。

### Ads 切换

先 Test 验证普通 purchase 与首购判定 -> 新版生产报告与真实首购收件核验 ->
GA 标记 first_purchase 为关键事件 -> Ads 导入并设为唯一主要，统计选择“仅一次”，
以首次客户数优化；原 purchase 改为次要，原订阅继续次要。
相应账号默认/系列目标需复核，只用首购出价；平台“仅一次”不能替代后台去重。
不提前关闭现有主要信号造成无可用转化，不重放既有16美元验收单。

### 验收

零现金后首次现金、历史老客、重复通知、并发首单、通知乱序、缺上下文首单、
退款后再购买、续费、升级、取消后再订、迁移未完成、账户重建、真/测试环境隔离。
首购一次、全部订单 purchase 正常、GA电商收入不翻倍、Ads仅一个主要目标。

## 3. 异常恢复与告警

### 发送与恢复

- 保留付款/注册/生成后的 after 即时发送；目标是正常 purchase/first_purchase
  在事实提交后一分钟内提交 Google 请求。失败不阻断付款或权益。
- 建议独立恢复任务每5分钟触发；每次按最早发生时间处理，批次50条，在35秒预算内
  循环、受总量和并发限制，不再固定只读20条。到预算即退出，下一次继续。
- 先核对 Vercel 计划：Pro/Enterprise 支持该频率，Hobby 仅每日；若计划受限，
  需选已授权外部定时器/升级后才能达到5分钟目标，不擅自开付费服务。
- 429 等明确可重试状态遵循 Retry-After；本地失败且请求未发送可重试，计划
  1/5/15/30/60分钟退避，加随机抖动并限制次数。区分可恢复错误与非法负载。
- 网络超时、5xx、进程终止可能已被 Google 接收，继续 uncertain 隔离；告警后对账，
  不盲目重发，尤其 first_purchase/custom事件不能假定拥有电商去重。
- 重试保留原发生时间和交易键，每次再核验上下文、授权、环境。缺失授权/标识
  不自动补报；超过协议时限标记过期。24小时会话归因目标与72小时回填区分。

### 健康与告警

- 新增受认证保护的健康接口，展示分状态数量、最旧年龄、传输延迟、上次worker成功
  和近24小时账单核验覆盖。不得公开用户ID、邮箱、哈希、client/session ID或秘密。
- 新增最小告警状态表，按环境+异常类型去重，记录首次发生/上次通知/恢复状态；
  同类持续故障30分钟冷却，恢复通知一次，持续24小时才汇总，避免邮件轰炸。
- 建议通知到项目告警邮箱，通过独立发送器或现有监控渠道；地址/服务接入需确认。
  仅结构化平台日志不能称为完成主动通知。未配置发送渠道时明确显示降级。
- 本轮只定义渠道，不发送真实消息，不创建其他平台账户或接受服务条款。

| 条件 | 等级/动作 |
| --- | --- |
| purchase/first_purchase pending 或 retry 超过10分钟 | 警告并继续安全恢复 |
| invalid、uncertain、异常 expired 出现 | 首次发现告警，附无敏感标识的故障类型 |
| 独立worker连续15分钟无成功执行 | 可用性告警；需要外部监控检测自身停机，不能只靠同一cron自检 |
| 距会话开始18小时仍未提交的可测量购买 | 高优先级归因时限告警，不改变原时间 |
| 已核验符合条件付款缺少内部报告事实 | 高优先级业务对账告警 |
| missing_context/拒绝授权 | 统计覆盖比例，属于预期测量限制，不逐笔当丢单轰炸 |

对账源优先完整 Stripe 付款事实；权益积分或 ProcessedStripeEvent 不能单独当付款账本。
对账区分应有内部事实与可测量上报数量，展示明确跳过原因，例如多行账单/无现金/
历史首购状态未知；不只统计已进入 AnalyticsReport 的记录而遗漏验证前跳过的账单。

### 验收

模拟429、400、5xx、超时、请求前失败、lease超时、重复worker、积压超过50条、
无新访问时恢复、撤回后重试、协议过期、告警去重/恢复/渠道未配置、任务自身停机。
Test中用假发送器和隔离数据，不向正式Google制造交易或强制重发未知接收记录。

## 4. 营销参数加固

- 将点击 ID 与 UTM 分开校验；点击 ID 允许 URL-safe 字符，单值初始上限512字符，
  不截断 ID，不人为改变字符；超长/非法值丢弃并记录无值的原因计数。
- UTM 单值上限200字符，允许规范化后的中文、空格和安全标点，统一正规URL编码；
  禁止控制字符、邮箱形态、嵌套URL、JWT/Token形态和异常敏感内容。
  语法不能保证识别所有个人信息，广告命名规则还须明确禁止包含用户/订单信息。
- 安全 query 总预算1500个编码字符，加域名与泛化路径不得超过平台page_location限制；
  超预算优先保留完整点击 ID，再保留 source/medium/campaign，最后 content/term，
  不通过截断点击 ID 假装保留归因。两个相互冲突的同名值保守丢弃该字段。
- 扩展公开入口 /pricing、/agent（仅精确公开入口），加上已有 /、/image、/video。
  /agent/私有会话、Assets、账户、未知路径继续泛化并移除查询参数。
- 保留现有 client/session 上下文链路，不为营销参数另建跨账户、跨周期无期限归因库；
  不强行把旧活动UTM粘贴到之后每页导致重写来源。
- 使用安全page_location与referrer控制所有手动事件；生产测试覆盖首次落地、
  客户端路由、根域跳转、Google登录、Stripe离站/返回、延迟同意、多标签。
- Ads/人工UTM字段建议命名规则：utm_source=google、utm_medium=cpc，campaign使用
  稳定活动ID或可读无隐私名称，content=素材/广告标识；人工UTM不能替代真实GCLID。

验收包含101/512/513字符点击值、中文与空格UTM、编码/重复字段/超预算、恶意输入、
Prompt/邮箱/session泄漏、私有路径、Google请求实际落地字段、独立Test环境收件。
