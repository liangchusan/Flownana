## 执行清单与固定顺序

按用户要求，以 GA 官方任务页为后台操作主线：开始使用 → 关联账号 → 增强报告 → 优化广告。每步先说明目标、当前进度及验收依据；完成当前步骤后再推进，网站改造统一安排，避免穿插临时切换。

1. 账号与环境：沿用正式 Flownana，独立 Test 资源；两个流的 ID 已截图核实。Test 时区、币种与保留设置仍待统一检查。
2. 开始使用 / 设置数据收集：完成后台流和 Google tag 配置准备，明确统一标签管理方式、按需自动采集、URL 清理和同意规则，并完成经批准的网站基础标签安装与真实收件验证。基础连接必须在进入关联账号步骤前完成；详细业务事件重建单独按规格验收。未实施前不把此任务标记为完成。
3. 关联账号：核对并关联现有正式 Google Ads；Test 不关联正式投放。关联与广告转化竞价分别验收。
4. 增强报告：确认全新事件字典、标准参数、必要自定义维度、关键事件及获客/漏斗/收入报表。注册、首次付费和生成事实必须明确，不靠界面自动推断。
5. 集中实施与验收：经详细规格确认后在测试测量环境实施；核对 DebugView、次数、金额、隐私与 Stripe，验收后下线旧发射点并进行批准的生产切换。此阶段属于网站改造，不混入后台逐页准备。
6. 优化广告：可靠首次付费作为唯一主竞价信号，核对金额、归因和去重；购买信号未验收前不启用竞价。受众、Google signals、用户提供数据及 BigQuery 按真实需要和同意条件另行安排，不为了完成全部任务自动启用。

当前已完成第 2 步的正式/测试数据流 ID 核对。用户任务页截图显示“与 Google Ads 相关联”锁定，助手先前跳到关联步骤的建议已撤回；这只确认该任务引导的当前状态，不推断所有 GA 关联入口都有同一限制。继续正式 Flownana 的“设置数据收集 / 采取行动”，核对安装说明并准备基础连接与收件；标签管理、自动采集、同意及网站改造规格仍需具体化，未进行部署。

经营核心为渠道/市场获客、注册到付款的漏斗、经 Stripe 核验的收入及广告获客成本；GA 任务计数不替代这些验收。

## 1. 要建立的测量体系

最终应能回答五个经营问题：

1. 哪个国家、关键词、广告和落地入口带来首次付费客户？
2. 用户是在登录、理解产品、体验生成、看套餐还是付款时流失？
3. 付费客户是否实际获得成功作品、持续使用并续费？
4. 获客成本加上生成、存储和支付成本后，这批客户是否赚钱？
5. 哪个流量组合应增加预算，哪个应降低预算或修复产品后再投？

推荐职责划分：

| 系统 | 用来回答的问题 | 不能替代的事实 |
| --- | --- | --- |
| Google Ads | 关键词、广告、花费、广告归因转化、竞价优化 | 全站真实付费人数、财务收入与利润 |
| GA4 | 获客渠道、用户行为、漏斗、跨渠道归因和受众 | 付款及媒体任务账本 |
| Stripe + 业务数据库 | 首次付费、续费、升级、退款、有效订阅、真实任务终态 | 无授权或无标识时的完整广告归因 |
| BigQuery，建议早期日导出 | 合并上述数据，计算 cohort、留存、净收入、成本与回本 | 自动得到 GA 界面的建模结果或 Ads 花费 |
| Looker Studio，后续按需要 | 展示统一定义的经营报表 | 修正源数据或自动拼接跨系统身份 |

推荐长期目标：**GA4 分析行为，Ads 用可靠的首次付费信号竞价，Stripe/业务数据验证经济结果。** 免费注册多、页面访问多，只能解释过程。

统一管理方向建议：共同使用 GA4，通用业务行为优先采用 Google 推荐事件名称与参数（如 sign_up、login、begin_checkout、purchase、refund），产品特有行为保留少量自定义事件；基础行为按需自动采集。推荐事件仍需网站/后台提供真实业务事实，不会因开启增强型衡量自动生成。GTM 可以集中管理标签投递与版本，但不能替代 Stripe 核验或真实注册/生成状态；是否迁移标签管理渠道另行决定。本段是方案建议，不能直接重命名旧事件、改变其含义或并行投递造成重复。

| 项目 | 当前证据 | 对分析/投放的影响 | 接入前处理意见 |
| --- | --- | --- | --- |
| GA4 基础 | 配置 `NEXT_PUBLIC_GA_MEASUREMENT_ID` 后加载 Google tag；已有页面和业务事件 | 已有基础，但后台属性、环境绑定及收件未在本轮核实 | 先盘点已有属性、标签和 Measurement ID，避免重复新建和重复加载 |
| 注册 | `signup_completed` 在组件观察到 authenticated 时触发 | 老用户登录/重新加载也可能被当成注册；不能计算真实新增账号 | 当前事件保留历史解释，另确认真实账号创建的 `sign_up` 与返回登录 `login` |
| 首页访问 | 首页每次路由效果执行可能触发 `landing_page_view` | 已登录用户回首页也可能计入；不是纯广告落地人数 | 广告入口按 GA landing page 与来源识别，区分游客/新客/回访 |
| Pricing | 当前是页面上的弹窗；已有 `pricing_viewed` | 用 `/pricing` 页面浏览来构建漏斗会漏掉真实套餐浏览 | 以弹窗事件测量，核验不同入口和打开次数；来源字段目前粒度不足 |
| Checkout | 当前 `checkout_started` 在发起接口前记录 | 表示发起尝试，不保证成功创建 Stripe Checkout | 保持原义；如需标准 `begin_checkout`，另定义可靠的结账可用事实 |
| 购买 | 已经服务端校验 Checkout 返回结果；浏览器本地按交易去重；最长重试约 20 秒 | 比 URL 成功标志可靠，但不回网站的付款会漏报；本地去重不能保证跨设备唯一 | 决定付费事实来源和统一交易唯一键，覆盖无返回、重复通知和重访 |
| 收入 | `purchase_success` 当前传 `payable_cents`、`credit_cents`、`currency`，没有标准 `value`/`items` | 不会自动成为标准电商购买收入；广告价值也不能直接用 cents | 确认标准 `purchase` 金额、币种、商品与购买类型契约 |
| 首购 | `purchase_type=new_subscription` 与 `upgrade` 已存在 | 新建订阅不等于该账号人生第一次付费；重新购买也可能是老客 | 首购必须依据账号历史成功付款识别 |
| 生成 | 产品约定任务组与逐输出的不同粒度；后台完成且浏览器未观察到时可能漏事件 | 四张图不是四位激活用户；事件成功数不是完整账本 | 用户激活按账号第一次成功；生成稳定性按后台输出终态 |
| 页面信息 | `/agent` 已做部分显式清理；其他页面仍可能包含完整 query | 账单 Session、搜索词、登录回调或私有链接可能进入 GA | 制定全站安全 URL、标题、referrer 与自动采集规则 |
| Consent | 在根标签加载代码中未看到同意状态控制 | 不能认定已有合格的分析/广告同意管理 | 核验现有隐私流程，确定地区策略和 Consent Mode |

## 4. 先确认指标，再决定标签

建议经营主指标控制在三个，额外数据只用于解释原因。

| 指标 | 推荐定义 | 主要用途 | 数据来源与限制 |
| --- | --- | --- | --- |
| 首次付费 CAC | 对齐获客 cohort 和观察窗的广告花费 ÷ 该 cohort 的首次付费账号数 | 判断买到一个付费新客的成本 | Ads 花费 + 业务首购；无归因客户单列，不能假装全被识别 |
| 注册后 7 日激活率 | 某注册 cohort 中，创建账号后 7×24 小时内获得至少一个成功且可访问图片/视频输出的账号数 ÷ 该 cohort 新账号数 | 判断用户是否拿到产品价值 | 账号创建和后台成功输出；排除测试账号，未满 7 日单列 |
| 获客 cohort 90 日贡献回报 | 该 cohort 90 日不含代收税的实收减现金退款/拒付、支付及实际服务变动成本，再减其广告费 | 判断是否值得持续扩量 | Stripe + 成本 + Ads；未满 90 日是阶段结果，不冒充最终 LTV |

辅助驱动：游客登录发起率/真实注册率、注册后 7 日首购率；首购后 7 日激活率；D7/D30 再创作留存；月付续费率和年付客户使用情况。严格控制首页仪表盘展示数量，其余放下钻。

护栏优先两个：现金退款/拒付；后台生成失败率。生成延迟和每位激活用户成本作为失败率与经济回报的诊断项。

几个关键区别：

- GA 的浏览器新用户不等于业务新账号，更不等于首次付费客户。
- 所有订阅订单数不等于新付费人数。取消后重订、升级、自动续费都不是新客。
- 输出数、任务组数、去重账号数是三种不同单位，报表名称必须写清。
- 下载点击不能证明下载完成，更不能直接证明商业满意度。
- 积分消耗不是 USD 成本；Provider 失败仍可能产生成本，退款积分也不代表 Provider 退费。
- 不强制把所有用户塞进一条顺序漏斗。有人先付费再创作，也有人先体验再买。

目前没有实际基线，先不承诺 CAC、ROAS 或激活率目标。可接受 CAC 应从目标回本期内的预期贡献毛利倒推，而不是从套餐标价倒推。报告同时给分子、分母、观察窗和未归因占比。

Ads 的归因首购 CPA 与业务中可关联的获客 cohort CAC 分别命名；DDA 分配的转化信用可能是小数，不代表后台出现了部分客户。广告归因回报也不直接证明增量回报，品牌流量和再营销尤其需要单独评估。

| 会话超时 | 初期保持默认；记录长任务行为 | 不为减少会话数随意拉长，生成留存按用户事件衡量 |
| 报告身份 | 登录后使用合规内部 User-ID；初期优先 Observed 解释可观察行为 | 之后按可用资格评估 Blended；建模数据与原始业务账本区分 |
| 关联产品 | Google Ads；已有 Search Console 可关联；建议尽早 BigQuery 日导出 | 关联本身不会自动完成转化和收入配置 |

数据保留与过滤依据：[GA4 数据保留](https://support.google.com/analytics/answer/7667196)、[GA4 数据过滤器](https://support.google.com/analytics/answer/13296761)。

环境隔离验收：Measurement ID、标签发布与分析投递目标分别配置；正式付款只能向正式属性及批准 Ads 动作报告，测试数据只能进 Test 属性，测试不关联真实竞价目标。如果使用 GTM，正式/测试发布目标也分别管理；如使用 BigQuery，数据集分开。不能只发一个 environment 参数后再用报表筛选来实现隔离。

本次确认的是测量与广告信号隔离，不代表当前业务数据库已经分开。现有本地/Preview 测试结账禁用规则继续适用；若未来要恢复端到端测试支付，应另规划独立测试账单数据边界，不能因建立 Test GA 属性就允许测试账单写入生产主库。

Google signals、广告个性化和 user-provided data 不建议为了“数据越多越好”全部打开。根据受众用途、同意状态和地区限制逐项启用、验收。没有它们也可以先做好基础流量和业务分析。

标签治理也要先选定：现有 Google tag 可以沿用；若计划持续投多渠道且需要投放人员管理标签，可选择 GTM 统一发布、版本和权限。两种方式都必须让可靠业务事件成为触发依据，不以按钮文本或 DOM 猜测付款成功；同一 GA 目标不能被现有 tag 与 GTM 重复发送。GTM 服务器容器和付费 server-side tagging 不列为一期必要项。

## 6. 增强型衡量：按网站实际行为选择

Flownana 是 SPA、包含私有会话和生成素材，自动采集尤其需要克制。

| 自动采集项 | 建议 | 注意点 |
| --- | --- | --- |
| 页面浏览 | 确保每次真实路由浏览只有一个责任方；既有手动追踪场景关闭自动 history 追踪 | 配合初始 config，验收首次打开/跳转/后退；不是简单关闭所有 page_view |
| Scroll | 可在有意义的公开内容页保留，工作台初期可关闭 | 90% 滚动不是阅读完成，不作为竞价转化 |
| Outbound clicks | 初期关闭全站自动采集，确有营销分析需求再对白名单公开链接启用 | 自动 link_url 可能带私有媒体地址、支付链接或 token |
| Site search | 初期关闭 | Assets 的 Prompt 搜索不应成为 GA 的 search_term |
| Form interactions | 初期关闭，关键表单按业务成功事实衡量 | 不能把 Prompt 提交当注册或付费 |
| Video engagement | 不依赖自动功能统计生成视频 | GA 增强型视频衡量针对支持 JS API 的 YouTube 嵌入，不自动覆盖本站原生生成视频 |
| File downloads | 初期关闭自动版本，保留安全的业务下载点击事件 | 自动规则并不完整覆盖图片；link_url/文件名也可能泄露私有信息 |

这些行为与字段见 [GA4 增强型衡量](https://support.google.com/analytics/answer/9216061)。自动 history 页面事件也可能绕过显式 `/agent` 清理，因此必须一起验证。

页面报告用稳定路由分类：Home、Image、Video、Agent、Assets、Billing、Account、Legal。私有会话统一为 `/agent` 或安全模板，不发真实会话 ID、会话标题、Prompt；账单页不发 Checkout Session 或完整回调 query。广告落地参数需在安全采集和归因保存中保留，不能在标签读取前一律删掉所有 query。

## 7. 事件与参数字典：确认目标口径

优先使用 GA 推荐事件名表达通用事实，保留 Flownana 自定义事件表达产品行为。下面是目标字典，不意味着本轮执行改名。

| 事件/信号 | 应表达的事实与粒度 | GA4/Ads 用途 |
| --- | --- | --- |
| `page_view` | 一次安全的页面/路由浏览 | 流量与页面路径；不做付费竞价目标 |
| `sign_up`，建议新增 | 后台首次成功创建一个账号；每账号一次 | 新注册 key event；Ads Secondary |
| `login`，建议新增 | 老账号一次成功登录 | 回访诊断；不当注册 |
| `signup_started`，已有 | 发起 Google 登录流程 | 登录漏斗；保留原义 |
| `signup_completed`，已有 | 当前是客户端观察到已登录，尚不能代表真实注册 | 历史诊断；先不导入 Ads 为新客转化 |
| `pricing_viewed`，已有 | 一次实际打开 Pricing 弹窗 | 转化意向诊断；记录入口，不做默认 Primary |
| `checkout_started`，已有 | 发起新订阅/升级请求尝试 | 接口前后漏斗，含失败尝试 |
| `begin_checkout`，可选新增 | 确认可用的 Checkout 被创建/复用并将进入付款流程 | 标准电商漏斗；不要直接把旧尝试事件别名映射过来 |
| `purchase`，建议新增 | 已核验成功付款，按唯一付款交易一次；含商品与金额 | 标准购买收入 key event，按首购/续费/升级下钻 |
| `purchase_success`，已有 | 当前已经核验且权益同步完成的 Checkout 返回 | 过渡验收使用；不与 purchase 重复作为同一竞价信号 |
| 首次付费信号 | 历史第一次成功现金付费的账号 | Ads 新客获客 Primary；不凭 new_subscription 推断 |
| `generation_started/success/failed`，已有 | 维持产品已定义的任务组/输出含义；补齐安全关联字段需确认 | 使用与稳定性诊断；重复输出不反复当激活转化 |
| `first_generation_success`，建议新增 | 账号首次获得至少一个成功可访问的图片/视频输出 | 用户激活 key event；Ads 默认 Secondary |
| `result_download_clicked`，已有 | 点击下载成功结果 | 价值使用诊断，Secondary 或不导入 |
| `insufficient_credits_shown`，已有 | 实际出现积分不足状态 | 升级意向与用户受阻诊断 |
| Agent 与 Template 已有事件 | 按 PRODUCT 各自含义记录；旧模板事件依入口是否仍存在核验 | 判断入口和理解/报价环节，默认不做 Primary |
| `refund`，建议新增 | 已核验的现金退款，支持部分退款与原交易关联 | 收入修正；生成失败退积分另计，不当现金退款 |

需要书面锁定的参数：

| 字段 | 建议值/用途 | 是否注册自定义维度 |
| --- | --- | --- |
| `creation_mode` | image / video / agent，指使用入口 | 是，事件级 |
| `media_type` | image / video，指实际输出 | 是，事件级；兼容当前 type 字段需确认 |
| `entry_point` | home / sidebar / user_menu / billing / insufficient_credits 等批准枚举 | 是，事件级；不与渠道 source 混用 |
| `model_id` | 稳定模型代码，统一当前 model/model_option_id 的解释 | 是，事件级；显示名另做字典 |
| `plan_id` / `billing_interval` | starter/pro/max；monthly/yearly | 是，事件级 |
| `purchase_type` | 首次订阅 / 重新订阅 / 续费 / 升级等批准枚举 | 是，事件级；与 is_first_purchase 分开 |
| `is_first_purchase` | 从账号全部成功付款历史判定的 boolean | 用于分群/转化条件，按实际查询需求注册 |
| `error_code` | 稳定错误分类，禁止 Provider 原文 | 是，事件级 |
| `template_id` | 稳定公开模板 ID，仅实际模板行为发送 | 有分析需求再注册 |
| `user_id` | 无直接身份信息的内部分析标识 | 使用 User-ID 功能，不做自定义维度 |
| `transaction_id` | 一个统一付款交易标识，前后端共用 | 用标准字段，不另做高基数维度 |
| `task_group_id/output_id` | 关联任务与输出，仅需要时发送安全内部标识 | 原始导出分析，不放常规自定义维度 |
| `output_count/duration_ms/credits_cost` | 数量、耗时、积分，单位明确 | 需要聚合时注册自定义指标，不拿 credits 当收入 |
| `event_version` | 切换后可识别口径版本 | 需要新旧比较时注册，另记录切换日期 |

所有字段形成事件字典：定义、触发条件、粒度、去重规则、参数枚举、同意要求、Owner、验收案例。字段“发出”不代表自动能在常规报表里分析；自定义定义通常要先注册。避免用户 ID、Session ID、时间戳等高基数维度导致报表聚合到 `(other)`。[自定义维度官方建议](https://support.google.com/analytics/answer/14240153)

身份规则：只在允许的同意状态下发送分析 User-ID；退出清除；切换账号不串联。GA4 的 User-ID 与增强型转化的用户提供数据是不同功能。邮箱、Google 登录原始标识、Prompt 不充当分析 User-ID，也不放普通事件参数。[User-ID 发送规则](https://developers.google.com/analytics/devguides/collection/ga4/user-id)

## 8. 收入、订阅和交易唯一性

标准 `purchase` 需要可靠 `transaction_id`、`currency`、以货币单位表达的 `value` 以及套餐 `items`。例如 USD 16 不能传成 1600；套餐编码可用 `starter_monthly`。税费与商品金额分别定义；后台实收与 GA 的商品收入如果不同，对账时必须能解释。[GA4 电商购买与退款](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce)

推荐区分三种数：首购实收、全部订阅实收、净收入/贡献毛利。年付首购记录本次实际收取的年费，不能当月收入、不能把“月均展示价”当交易金额。用户升级只记录此次实际新增付款，不能重复记录抵扣前标价；零付款变更不作为新付费获客转化。

年付实收并不代表年付客户必然利润更高：还承担未来服务成本。第一阶段 Ads 用实际首购金额；成熟后若需价值竞价，可另建立经过验证的贡献价值信号，不能篡改 GA 财务收入，也不能把预估 LTV 和实际收款同时相加。

现金退款要同时考虑 Ads 主转化价值修正：不能假设 GA 的 refund 自动修正另一条原生 Ads 购买动作。按选定来源的支持能力，确认部分退款 restate、全额退款/无效购买 retract 的处理边界、时限与交易映射。期末取消订阅但不退钱，不等于撤销已经成功收取的首购。[Ads 转化调整规则](https://support.google.com/google-ads/answer/7686447)

交易约定要覆盖首次付款、重订、升级、续费、补付、部分退款。当前返回事件使用 Checkout Session ID；若未来统一以 invoice/payment 作为付款事实，要在切换前建立对应和去重规则。不能假设不同 ID 的前端与服务端事件会被 GA 自动合并。

推荐付款覆盖目标：付款事实从可信后台确认；浏览器返回用于界面与体验测量；不返回也能在允许的条件下形成业务付款记录及分析信号。向 GA/Ads 报告仍受同意、标识和平台归因规则约束。

### 8.1 Stripe 再核验与购买上报边界

采用用户提出的 Stripe 再核验原则，推荐业务要求如下，具体接入实现另行设计：

1. **付款通知只是触发核验。** 后台接收并验证 Stripe Webhook 签名，通过 Stripe API 回读关联 Checkout、Invoice 及实际付款对象；返回页可复用同一核验能力。Webhook 验签证明通知来源，Stripe 回读用于确认对象、归属、状态和金额，两者用途不同。
2. **区分环境与归属。** 核对正式 Stripe 账户/Live 模式、内部账号与 Customer/Subscription 归属、批准套餐、币种及交易对应；Test 交易不得进入正式 GA/Ads。
3. **确认实际付款。** Checkout complete、订阅 active 或出现 invoice.paid 通知，都不能单独替代现金付款核验。核验相应 Invoice/付款对象及实际收取金额；零金额、余额抵扣、手动标为已付但没有实际 Stripe 收款的情况不能冒充现金首购。异常待确认时暂不上报成功，待核验恢复后处理。
4. **唯一交易只报告一次。** Webhook 重试、Checkout 返回、补付核验、不同 Stripe 事件和不同浏览器观察到同一付款，都应关联到一个统一交易。持久化记录核验与报告状态；业务层保证幂等、使用相同下游交易 ID 去重，并能发现投递失败。不能只靠 localStorage，也不能宣称不同平台自动提供绝对 exactly-once 保证。
5. **重新判定首购与类型。** 以账号历史成功现金付款判定首次付费；之后的续费、升级、重新订阅另分类。用户不返回网站也能完成付款核验，但是否向 GA/Ads 报告仍以授权和可用标识为前提。
6. **报告与付款处理分开。** GA/Ads 上报失败不能阻止付款核验和积分/权益发放；核验结果与待报告状态需可追踪。后续现金退款修正相应收入/广告价值。

Stripe 官方要求可靠处理不依赖用户返回网站，并指出 Webhook 会重试、重复且可能乱序；因此回读、业务去重和无返回覆盖应一起设计。[Checkout 付款处理](https://docs.stripe.com/checkout/fulfillment.md?payment-ui=stripe-hosted)、[Webhook 验签、重复与乱序](https://docs.stripe.com/webhooks)

这里要保留两个状态：**Stripe 已核验收款**与**网站权益同步完成**。推荐新标准 `purchase` 表达已核验付款事实，权益完成作为独立状态诊断；这项触发口径尚待单独确认。原 `purchase_success` 仍按 PRODUCT 要求，只在已核验且权益同步完成的 Checkout 返回中触发。在正式批准新口径前不能用新方案改变旧事件。

这会超出当前“Checkout 返回且权益同步完成才报 purchase_success”的批准规则，必须另确认新事件和完成状态的边界。暂不增加复杂基础设施；先列出覆盖要求，再选择满足要求的最小实现。

特别注意：只把 Stripe Webhook 发给 GA，并不会自然获得正确广告来源。会话归因需要满足 Measurement Protocol 对客户端/会话标识与时点的要求；自动续费不能硬绑定一个过期访问会话。对于无标识/无授权交易保留后台事实、单列覆盖缺口。[Measurement Protocol 用途与会话归因要求](https://developers.google.com/analytics/devguides/collection/protocol/ga4/use-cases)

## 9. Google Ads：到底优化什么

GA4 的事件、key event 与 Google Ads 转化不是同一个设置。标为 GA key event 不等于已经被广告竞价采用。[Google 对 key events 与 conversions 的定义](https://support.google.com/analytics/answer/13965727)

推荐目标配置：

| Ads 转化动作 | Primary / Secondary | 类别/计数 | 金额 | 用途 |
| --- | --- | --- | --- | --- |
| First paid subscription：账号首次成功付费 | **Primary，默认获客目标** | Purchase / Every；业务层每账号首购一次，交易唯一 | 实际首购金额与币种 | 首轮付费获客 |
| 同一首购的 GA4 导入版本，如果保留 | Secondary | 相同首购口径 | 相同金额 | 比较覆盖/归因；不能与主来源相加 |
| All subscription payments | Secondary，或不导入 | Purchase / Every，交易唯一 | 全部实际付款 | 总收入观察，避免续费冒充获客 |
| Sign up | Secondary | Sign-up / One | 不虚构营业收入 | 登录/注册质量 |
| First successful generation | Secondary | 按支持的类别选择 / One | 初期不设置猜测价值 | 激活质量 |
| Pricing、Checkout、Download | 不导入或 Secondary | 按实际观察需求 | 不赋同等购买价值 | 漏斗诊断 |

这里的 Every/One 都是广告互动后的计数设置；One 不是“一个账号一生一次”。首次付费唯一性必须由业务事实保证。同一广告点击后若发生多笔真实收入，All payments 应保留 Every；新客事件则天然只有首笔。[计数与日期口径](https://support.google.com/google-ads/answer/2375435)

**推荐的长期主来源**：Google Ads 原生首次付费转化 + 经授权的增强型转化；GA4 标准购买事件负责全站分析。如需 GA4 导入相同首购，只设 Secondary 用于比较。

如果初期只准备 GA4 导入，也可以用同一个可靠首购作为唯一 Primary，条件是通过完整验收。以后切换主来源时做一段并行观察、记录生效时间，一次只保留一个首购竞价来源。不能同时让原生和导入版本都成为 Primary。“All conversions”含观察动作与重复来源，不能直接当付费人数。

每个获客 campaign 都应明确只选择首次付费目标。检查 account-default goals 和 campaign-specific goals；不要因把注册放在 Secondary 就认为永远不会参与竞价：**加入 custom goal 的 Secondary 仍会用于竞价**。[Primary/Secondary 官方规则](https://support.google.com/google-ads/answer/11461796)

起始参数建议：首购点击转化窗 30 日；GA 对相关购买 key event 的回溯窗也确认并记录。若后台启用新版本统一转换管理，有的窗口/计数需在 GA 中维护，以实际账户界面为准。DDA 可用时用于常规归因，并保留末次点击对照。视频展示与互动观看转化单独查看，不和 Search 点击效果混成一个 CAC。

30 日是没有真实延迟数据时的起点，之后用 click→首购的延迟分布复核；不要缩窗来“提高效率”或拉窗来“增加转化数”。GA 与 Ads 的渠道、窗口及计数控制位置已有更新，实际配置需核对。[归因配置](https://support.google.com/analytics/answer/10597962)、[Ads 转化窗口](https://support.google.com/google-ads/answer/3123169)

## 10. 归因与营销命名

Ads 开启 auto-tagging，并完成 GA4↔Ads 关联、转化目标与必要的受众共享设置。不要靠手填 `utm_source=google` 替代自动标记。关联后仍要验证花费、campaign 信息与转化实际出现。[GA4 与 Ads 关联](https://support.google.com/analytics/answer/9379420)、[自动标记](https://support.google.com/google-ads/answer/3095550)

保留平台提供的 `gclid`、`gbraid`、`wbraid` 及 UTM，在符合授权的前提下让其经过域名规范化、首次跳转与登录承接。不是要求所有下游页面永远显示参数，而是不要在合法测量读取前丢掉它们。不能为了测试归因随意伪造 GCLID，然后把“显示了参数”当成 Ads 归因成功。[重定向丢失点击数据](https://support.google.com/google-ads/answer/15629968)

UTM 用于非 Google 渠道，也可为 Google 广告补充稳定营销命名。建议全小写、固定枚举，记录 campaign ID；重命名不应改变历史主键。

| 字段 | 示例，仅为命名示意 |
| --- | --- |
| utm_source | newsletter / youtube / partner_name |
| utm_medium | email / paid_social / referral，使用可正确归入渠道的值 |
| utm_campaign | us_image_prospecting_2026q4 |
| utm_id | 自有稳定 campaign ID；Google Ads 优先使用平台 ID |
| utm_content | demo_image_before_after_v1 |
| utm_term | 有需要才记录；不可放用户 Prompt |

Google Ads 如需补充参数，使用经核验的 ValueTrack/URL suffix，避免自动标记与人工参数互相矛盾。品牌词/非品牌词、新客/再营销、主要市场和创作诉求应能区分。预算少时不要拆出大量无法学习的小 campaign。

四个已确认市场建议在一个正式 GA 属性内统一衡量，市场代码采用 US/JP/KR/TW，按国家、广告目标市场、浏览器语言及实际页面语言分别下钻。地理位置不等于语言；四个市场的报表都采用洛杉矶日期口径。广告与落地语言匹配建议为英语、日语、韩语、繁体中文；语言页面是否需要开发另行确认，不能假设当前网站已本地化。预算允许时可按国家/语言控制 campaign 预算，但不因此创建四个 Analytics 属性或四个 Ads 账户。

站内导航不加营销 UTM；站内入口用 entry_point。保留首次获客和当前会话两种视角：First user 来源解释最初怎么认识网站，Session 来源解释这次怎么回来，事件归因解释转化前的贡献。三者不能混用。

## 11. Google 登录与 Stripe：不能让流程域名抢走渠道

不需要把普通第三方 Google 登录域名和 Stripe Checkout 加进“跨域衡量”的列表来解决问题。跨域衡量用于自己控制、能部署一致标签的多个站点；不是任意第三方域名名单。

应做三件事：

1. 验收广告落地→Google 登录→恢复原页面/套餐→付款返回的来源和用户连续性。
2. 在 unwanted referrals 中仅加入经验证属于支付/认证流程的域名或精确匹配条件，例如实际出现的 Stripe Checkout 域名；不要粗暴排除整个 google.com，以免误伤真实 Google 引荐。
3. 用户付费后即使未返回，也能在后台确认为同一交易；如果无法合法归因，保留未归因交易，不用 Direct/Stripe 伪装已知来源。

排除不需要的 referral 可以防止流程域名成为新引荐来源，但不能找回已经丢失的用户标识或原广告点击。[GA4 不需要的引荐流量](https://support.google.com/analytics/answer/10327750)

## 12. 同意、隐私与增强型转化

先确定用户能选择什么，再配置采集。至少区分：必要功能、分析、广告数据使用、个性化广告；拒绝和撤回都应有明确入口。Google 登录成功不代表用户同意广告用途。

涉及 EEA、英国、瑞士用户时，要按 Google EU User Consent Policy 核对披露与同意要求；美国及其他市场的要求按实际投放/访问地区核实。不能因为公司或服务器在其他地区就忽略用户所在地。[Google EU 同意政策说明](https://www.google.com/about/company/user-consent-policy-help/)

Consent Mode 要覆盖 `analytics_storage`、`ad_storage`、`ad_user_data`、`ad_personalization`。CMP/同意界面收集选择，Consent Mode 向标签传递选择；二者不能互相替代。

| 方案 | 行为 | 选择建议 |
| --- | --- | --- |
| Basic | 未授权时阻止相关 Google 标签和数据发送 | 若要求拒绝后完全不向 Google 发送，采用此方式 |
| Advanced | 默认拒绝时仍可能发送无 Cookie 的测量信号；授权后按选择采集 | 在地区策略与隐私审查支持时优先评估，可改善测量覆盖；不是“没有传数据” |

两种方式的区别来自 [Google Consent Mode 官方说明](https://developers.google.com/tag-platform/security/concepts/consent-mode)。小网站不应假设启用 Advanced 就立即获得完整建模或能恢复每笔丢失转化。

增强型转化可在允许情况下使用已有第一方数据，例如登录邮箱，通过专门渠道规范化/哈希匹配，提升 Ads 的测量覆盖。不要额外强迫用户补手机号，不用普通 GA 参数发送邮箱，也不把哈希视为免除同意要求。

建议先对 Ads 主转化按明确字段白名单启用和验收，避免在 Prompt、会话和 Account 页面全站自动扫描身份信息。Google 自 2026 年 4 月开始统一增强型转化设置，实际界面可能不同于旧教程；GA 的用户提供数据能力也需单独确认，不能假设在一端打开就两端都完成。[当前 Ads 增强型转化设置](https://support.google.com/google-ads/answer/13262500)、[GA 增强型转化](https://support.google.com/analytics/answer/14252663)

全站数据防泄露清单：邮箱/姓名/Google 身份标识、Prompt/Agent 对话/搜索词、上传素材 URL、签名媒体 URL、Checkout Session/授权 code/token、带身份信息的页面标题/referrer。GA 后台开启邮箱和指定 URL 参数 redaction 作兜底；服务端/Measurement Protocol 仍需自行清理，后台 redaction 不覆盖这些渠道。[GA4 数据脱敏能力与限制](https://support.google.com/analytics/answer/13544947)

## 13. 受众：先为后续投放建立规则

下列天数都是 Flownana 起始建议，以购买周期与实际名单规模调整。

| 受众 | 起始定义 | 用途与限制 |
| --- | --- | --- |
| 看过套餐但未首购 | 近 7/30 日 pricing_viewed，排除首次付费 | 价格/价值沟通；避免继续追逐已付费者 |
| 发起结账未付款 | 近 7 日可靠 Checkout 意向，排除成功购买 | 高意向恢复；不把支付失败客户无限投放 |
| 新注册未激活 | 注册 7 日内未产生成功输出，排除已激活 | 引导价值体验；需要真实注册/激活信号 |
| 已激活未付费 | 有首个成功输出，未首次付费 | 从体验转为购买 |
| Image / Video / Agent 使用者 | 近 30 日实际业务行为 | 创作诉求匹配；低量时作为观察，不细拆预算 |
| 付费客户 | 有可靠付费事实，另区分当前有效订阅 | 新客 campaign 排除/独立运营；升级与续费单独目标 |
| 退款/异常客户 | 按后台确认的业务状态，仅在规则允许时使用 | 经营诊断；不依据 Prompt 推断敏感人群 |

尽早建受众以积累后续可用名单，但不保证所有历史数据自动进入、也不保证马上可投。Ads 是否能使用取决于同意、政策、名单规模和账户资格；现有付费者要覆盖完整首购/续费事实，不能仅依赖浏览器返回事件。

GA4 受众有更新延迟，不能作为实时账单状态。生命周期运营/实时权限仍以后台为准。分析可看包含未授权广告用户的合法业务统计，Ads 定向名单只能使用允许用于广告的部分。

## 14. 先建四张报表，每张都要对应动作

| 报表 | 主要内容 | 要做的决定 |
| --- | --- | --- |
| 获客质量 | 渠道/campaign/关键词/国家/设备/落地入口；花费、新账号、首次付费、首购价值、CAC | 哪些组合加预算/减预算 |
| 商业漏斗 | 广告入口→登录发起→真实注册→Pricing→可靠 Checkout→首购；事件级来源和阶段耗时 | 修哪里能提高付费 |
| 产品价值与留存 | 注册 cohort 的 7 日首个成功输出；先体验/先付款两类路径；首购后激活、D7/D30 再创作 | 广告带来的人是否拿到价值 |
| 经济与数据健康 | 首购/续费/升级净收入、真实变动成本、退款；后台付款 vs GA/Ads 可测量付款、延迟与重复 | 能否扩量，以及是否要先修测量 |

商业漏斗同时提供从广告入口开始的 closed funnel 和从任意阶段进入的 open funnel。按账号/用户去重，不直接用事件数量相除。明确使用同会话、7 日或30日转化窗，不能把同一天任意用户的注册与购买拼起来。

留存建议：D7 用首次激活后第 7 个报告日是否再次成功创作，另看第 1–7 日是否再创作的窗口留存；D30 同理。两种定义分别命名，时区固定。注册和付费转化窗用 elapsed time，避免与日历日口径混淆。

建一张经营周表：花费、可归因新付费客户、未归因新付费客户、CAC、首购实收、月/年付占比、激活率、现金退款、成熟 cohort 贡献回报。收入和成本跨系统合并后再展示，不能直接把 GA、Ads、Stripe 三个数字横向相加。

## 15. BigQuery：建议早期保留原始数据，不先造重型数仓

建议从正式采集开始尽早开启每日导出，Streaming 初期通常没有必要。先保留原始数据和事件字典，再按确有需求建立最少的经营查询。

需要提前确定 Google Cloud 付款归属、数据区域、访问权限、保留期限和预算告警。免费额度/免费 Sandbox 不等于无限免费长期保留；不要把未来补齐完整历史原始数据当作保障。GA 保留 14 个月也不能代替自己管理导出数据的保留政策。

之后要合并三类数据：GA 事件、Ads 花费/广告维度、Stripe/业务付款和实际服务成本。Ads 链接不会自动让 BigQuery GA 导出包含广告花费；成本源、身份映射和订单关联都要单独准备。原始导出与 GA 界面建模/归因数字也可能不同。[BigQuery 导出设置](https://support.google.com/analytics/answer/9823238)、[导出内容与报表区别](https://support.google.com/analytics/answer/9358801)

## 16. 投放学习怎样安排才不浪费钱

先按明确创作诉求评估获客；品牌和非品牌、新客和再营销分别看，避免品牌回流掩盖新客购买成本。需要拆分的是经营差异，不是每一个模型或按钮。

起步以唯一首购目标观察，竞价策略按账户适用资格、预算和真实转换量选择。初期缺数据不宜设置未经测算的苛刻 tCPA/tROAS，也不采用“所有账户到固定 30 次转化必然切策略”的规则。关注完整转化周期和信号稳定性，而不是每天波动。

如果首购太少，先排查广告意图、落地体验、价格、支付和追踪覆盖。只有首个成功生成与后续付费存在可验证关系时，才考虑在独立学习 campaign 临时用激活作 Primary；主经营报表仍看首购 CAC，明确代理目标的退出条件。不要把注册/点击全部升成 Primary 制造好看的转化数。

当收款价值、月/年付结构和覆盖稳定后再评估价值竞价。使用实际首购收入时额外检查退款与未来服务成本；采用预测贡献价值时需独立验证模型，不能宣称是实际 ROAS。

每次改变转化来源、主目标、金额口径或窗口，都登记日期、Owner 和原因，并留出充分观察期。Google 的竞价标签与转化管理正在更新，界面名称不等于算法行为改变；不要为了追教程频繁切换。[调整竞价转化目标的官方建议](https://support.google.com/google-ads/answer/14571185)

## 17. 接入与投放前的验收清单

这是一份未来验收要求，本轮未执行浏览器/付款/GA 后台测试。

| 手动场景 | 预期证据 |
| --- | --- |
| 桌面/手机首次打开、SPA 跳转、前进后退 | 每次有效路由只有一次 page_view；无私有 URL/标题；慢加载仍正确采集 |
| 首次注册、老用户登录、刷新、退出/换账号 | 真实 sign_up 每新账号一次，旧登录不计新增，身份不串号 |
| Sidebar、用户菜单、余额不足等入口打开 Pricing | pricing_viewed 正确，入口准确；弹窗不冒充独立页面 |
| 新购与升级接口失败/取消/重试 | 尝试与可靠 Checkout 区分；未付款不报购买；重试不造新交易 |
| 经授权的正式首购（月付/年付） | Stripe API 再核验真实付款/金额/币种/归属；后台交易唯一，GA 金额与货币单位正确，Ads 首购动作准确 |
| 同一交易刷新、返回、跨标签/设备与重复通知 | 交易不重复；首购账号只算一次；主来源与观察来源分开 |
| 已付款不返回、Webhook 延迟、权益同步中、Hosted Invoice 补付 | 后台事实准确，分析覆盖按批准完成条件；无假成功，能解释延迟/漏报 |
| 升级、重新订阅、自动续费、现金部分/全额退款 | 分类准确，老客不变新客；净收入可核对；积分退款不当现金退款 |
| Image/Video/Agent，四图部分成功，关页后完成 | 用户首个成功一次；组/输出粒度正确；后台终态与可观察事件差异可解释 |
| 广告落地→域名跳转→Google 登录→Stripe→返回 | 平台点击与来源未丢；Google 登录/Stripe 不抢走归因 |
| 同意全部、拒绝全部、仅分析、撤回，再次访问 | 与 Basic/Advanced 选择一致；拒绝广告不再做增强型匹配/个性化用途 |
| Preview/本地/内部 QA | 不污染 Production 与主 Ads 转化；过滤先测试再启用 |
| 四市场及洛杉矶午夜/夏令时边界 | 国家/语言维度准确；GA、Ads、付款日报按 America/Los_Angeles 对齐，事件不因 UTC−8 固定偏移落错日期 |
| GA4→Ads 或原生 Ads 主转化 | 标签诊断正常、必要延迟后动作收到；campaign 只使用批准主目标 |

工具证据：Tag Assistant/DebugView 查看事件内容和同意状态；GA4 常规报表确认处理后数据；Ads 转化诊断/动作设置确认实际收件与竞价范围；Stripe/数据库核对订单。Realtime 出现事件不是收入、归因、竞价全部验收通过。

实际付款测试单独授权；当前本地和 Preview 测试结账已被产品/工程规则禁用，不能把它们随手开启来测 GA。先用 Test 属性做非付款验证，正式全链路需在批准的环境和付款边界下安排。

## 18. 对账与剩余风险

对账顺序：后台成功付款交易→其中满足同意与标识条件的可测量交易→GA 可观察 purchase→Google Ads 归因首购。以交易维度检查重复、金额、类型与延迟；不是要求总量永远相等。

固定报告时区、日期窗口、计数、归因来源和货币。Ads 默认按导致转化的广告互动日期回填；比较交易当日收入时，使用对应动作的“by conversion time”列。不要拿含重复观察来源的 All conversions 总数对比 Stripe 订单数。[Google Ads/GA 转化日期与计数差异](https://support.google.com/google-ads/answer/2375435)

剩余风险：

- 同意拒绝、广告拦截、浏览器限制、跨设备和丢失标识导致无法完整观测；增强型转化与建模不保证每笔恢复。
- 小样本、晚到转化、现金退款、年付服务成本和未成熟 cohort，容易导致过早扩量。
- 当前只有客户端返回购买报告，注册与输出粒度仍有歧义；未解决前不适合直接用来自动竞价。
- 当前工作区包含已发布但未提交变更，本轮静态审阅不证明生产每个事件版本一致。
- 标准事件/新增身份关联/服务端完成事件需要产品批准；新增同意 UI 也需独立确认范围。
- 现有 Ads/GA4 资产与后台设置未读；部署 ID 和应用事件存在并不证明 Measurement ID、重复标签或转化管理正确。

## 19. 推荐推进顺序与完成标准

1. **确认测量口径。** 交付事件字典、首购/激活/收入定义、隐私与市场范围、指标和 Owner。完成标准是产品与投放用同一套定义。
2. **准备账号与后台设置。** 核验资产所有权、时区币种、属性与环境隔离、留存/过滤/自动采集/归因/关联；受众与日导出按批准设置。完成标准是有可回读的设置清单。
3. **单独确认接入开发。** 按此方案选定最小范围写入 PRODUCT，再实施必要事件和同意逻辑。完成标准是完整验收和数据质量说明；本稿不构成开发批准。
4. **小预算验证首购信号。** 核验实际投放归因、唯一主转化、付费漏斗和成本。完成标准是可以解释一批真实用户从广告到付款/激活的结果。
5. **有证据再扩量。** 看成熟窗口的首购 CAC、激活、退款、续费和贡献回报；据此决定受众、价值竞价与进一步分析。
