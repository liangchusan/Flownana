## 结论与证据边界

用户反馈线上已登录时所有页面跳转慢，使用 VPN，其他网站正常。本次完成代码审查、生产部署核对、匿名 HTTP 采样、线上资源检查及数据库只读统计检查。没有修改应用代码、生产配置、数据库数据或产品规则。

主要嫌疑链路是：美国东部函数 → 东京数据库的多次串行往返 → 历史/会话读取同步执行恢复任务并取得账号排他锁 → 页面缺少覆盖上述等待的加载状态。结构问题已由代码确认，历史账号锁长耗时也有数据库统计证据；各环节对本次用户操作的毫秒贡献尚未实测。

浏览器控制连续两次超时，没有获取已登录浏览器的 Performance/Network 瀑布、INP、LCP 或点击到页面提交耗时。因此不声称已复现所有跳转，不把匿名请求耗时当作登录态耗时，也不把累计 SQL 最大值当作用户这一次的等待。

## 按优先级排列的问题

### 1. 跨区域往返被串行数据库操作放大

`app/_components/media-workspace-page.tsx:23` 在返回工作台前依次等待 `getServerSession` 和 `getCreationHistory`。JWT 回调也会在 `lib/auth-options.ts` / `lib/account-session.ts` 查数据库验证账号仍存在及注册时间。

`lib/creations.ts:82` 先执行恢复，再进入带账号锁的历史查询。即使没有异常任务，恢复仍检查过期任务、失败退款和媒体清理候选，随后历史查询还有关联媒体读取；并非一次数据库读取即可完成。每次事务内的顺序请求及开始/提交都会受到跨区域往返影响。

建议：先补阶段计时，单独验证把应用函数与数据库放在同一区域的收益；再减少读取路径的往返。不要为了少查一次直接删除账号撤销/注册时间验证，也不要跨账号缓存私有结果。

### 2. 读接口同步恢复并争用同一账号排他锁

- `lib/generation-lifecycle.ts:64` 的 `withGenerationAccount` 使用 `SELECT ... FROM "User" ... FOR UPDATE`，事务 maxWait 5 秒、timeout 默认 15 秒。
- `lib/creations.ts:71` 的读取先执行恢复；没有清理候选时也会进入一次清理检查事务，再进入一次历史读取事务。
- `lib/agent/service.ts:31` 的 `readAgent` 同样先恢复，然后在账号锁内更新过期 Agent 回合、读取会话列表、套餐额度、会话详情和输出。仅侧栏列表查询也走此路径。
- `lib/billing-summary.ts` 使用 `withBillingUser`，取得同一个 User 行锁；这些读取会与生成预约、退款等写入互相排队。
- 有待清理输出时，历史读取还会等待 Blob 删除，单次外部删除设置 15 秒超时。该网络 I/O 在清理事务之外，不能误称持锁等待 Blob，但它仍在读取响应的关键路径上。

线上 `pg_stat_statements`（应用角色 `flownana_app`）采样：

| 类别 | 调用次数 | 平均数据库执行时间 | 最大执行时间 |
| --- | ---: | ---: | ---: |
| User FOR UPDATE | 27,475 | 57.978 ms | 9,351.53 ms |
| Generation 查询分类 | 54,555 | 0.170 ms | 25.95 ms |
| User 非锁查询分类 | 41,860 | 0.102 ms | 589.99 ms |
| Agent 查询分类 | 1,034 | 0.146 ms | 6.84 ms |

统计重置时间为 2026-05-18 09:16:58 UTC，各查询采样时刻略有不同。这些是累计分类统计，包含旧版本，不能视为本次操作或当前版本的 p95；分类基于归一化 SQL 中表名，非精确业务 span。User 行锁累计耗时远高于普通查询，支持历史上存在锁竞争的判断。

`pg_stat_user_tables` 估计 Generation 43 行、AgentTurn 4 行，暂无证据支持“表太大导致慢”。即时活动快照中应用连接空闲，未捕捉到正在发生的锁等待；也没有证据证明连接池耗尽。不能因小表顺序扫描多就直接增加索引。

建议：将安全的纯展示读取与恢复/写入拆开，缩短锁内工作；恢复不能直接删除，必须保留退款、租约、清理最终完成的机制。实际实现需独立评估账号删除/重新注册、并发生成和跨账号隔离。

### 3. 页面加载反馈没有覆盖真正慢的部分

仓库 `app/` 只有根 layout，没有任何 `loading.tsx`。工作台内部的 `Suspense` 位于 session/history await 之后，所以不能覆盖这些等待；根布局的 Suspense 只包 Analytics。跳转到需要服务端数据的页面时，用户可能一直看到旧页面。

建议：给动态页面加合适的路由级 loading，将异步数据放在能被边界覆盖的位置；保持导航壳可交互。加载反馈可改善体感，但不会自动减少数据库总耗时。

参考：[Next.js 官方导航说明](https://nextjs.org/docs/app/getting-started/linking-and-navigating)，以及本地 Next 16.3.3 的 `node_modules/next/dist/docs/01-app/01-getting-started/04-linking-and-navigating.md`。

### 4. 页面进入后重复读取与后台轮询放大负载

- 根 Providers 没有从 RootLayout 收到服务端 session；`SessionBoundary` 仅返回 children。客户端仍需要独立获取 session，之后才开始受保护的数据请求。
- 工作台已有服务端历史种子，客户端挂载后仍立即调用 `/api/creations`，随后每次完成后等待 10 秒再刷新，即使没有活跃任务也继续。
- `components/blocks/agent/agent-history.tsx:25` 在 scope 或 pathname 变化时重新读列表，并每 15 秒刷新。AgentWorkspace 还有独立会话轮询；未选择会话时，两者都可能读取 `/api/agent` 列表。列表读取没有共享请求去重。
- Agent 活跃回合轮询间隔为请求完成后 1.5 秒，活跃媒体为 3 秒，空闲 15 秒。每轮会话读取都包含上面的恢复和锁工作。
- Billing 客户端已经有 60 秒按账号缓存和在途请求去重，不能笼统认定所有共享数据都没有缓存。

建议：复用可靠的账号 scoped 初始数据、合并会话列表请求、减少空闲轮询，并在任务完成、额度变更和账号变化时正确失效。页面预取是否造成额外恢复负载，需要已登录瀑布进一步确认；仅凭日志里有多个路由请求不能确定它们全是预取。

### 5. 前端资源有次要优化点，尚未证明是每次跳转的主因

- 当前线上首页 HTML 引用的 15 个 JS/CSS 资源全部下载成功，总解压体积 1,043,861 字节；本地 gzip 估算 310,288 字节。这不是实测浏览器传输总量，未计图片、字体、GA 或后续动态资源。
- 工作台静态导入图片/视频表单、Assets、AgentComposer 等组件，可进一步评估延迟加载；目前没有浏览器 CPU profile，不能认定 JS 是主因。
- `app/globals.css:1` 及下载的生产 CSS 都保留 Google Fonts 外部 `@import`，增加首屏外部样式请求依赖。适合改为自托管字体，但未实测其耗时；已缓存字体不能解释每次页面切换都慢。
- 模板封面已使用 `next/image`、响应式 sizes 和默认懒加载，不能按原始 PNG 总体积直接计算首屏下载量。
- GA 脚本使用 afterInteractive，未发现导航 handler 等待 GA 网络完成；没有证据把 GA 或模型推理当成普通页面跳转的根因。

## 优化顺序与风险

建议顺序：阶段计时与加载反馈 → 单独验证函数数据库同区 → 拆分读取与恢复、减少锁内往返 → 合并空闲轮询 → 字体和包体优化。这里是诊断建议，尚未实施或承诺量化收益。

主要风险：直接移除账号锁或恢复可能损坏退款/并发预约/删号安全；缓存不当可能出现串号或旧余额；减少轮询可能延迟任务完成展示；迁移函数区域需要验证数据库、Blob、Stripe、Provider 回调及生成链路。没有真实登录浏览器样本前，仍不能完整解释用户所说的“所有页面”。
